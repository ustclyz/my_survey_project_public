# 必观测救援策略 v1

基于 exp/duty-log 84258a9，加上本地 duty-delivery 修复。
目标：争取 B1 相对 pro-fast-fault-v4 净增 10000 分。尚未官方评测，目标未确认实现。

策略变化（由长值班日志启用，普通卡默认保持原策略）：

1. 正确报修后立即恢复质量先验、清除必观测失败次数和失败标定；保留真实已得分记录、指向偏移及几何失配记录。
2. 必观测目标的失败折扣最低为 0.25，避免长期失败后永久失去调度机会。
3. 为接近最后可见夜的未完成必观测目标保留候选名额；最终仍按视场收益和时间成本选择，并非强制逐个拍。
4. 根据当前质量、亮度及质量随曝光长度的变化，计算达到完成因子 0.675 的最短候选曝光，向上取整到 30 秒；每个视场最多增加四个候选。无法在高度角/维护窗口内达标的目标不增加候选。
5. 质量估计低于 0.15 时将规划窗口限制为 300 秒，用较短曝光获取诊断信息；保留已有日志报修和统计报修。

这不是完整的跨夜最优解：使用已有的最后可见夜与机会折扣，没有假设知道未来隐藏天气。

## 本地对照

使用 tools/rescue_probe.py，cardB 前两晚、相同目录数据和模拟时长。
简化反馈假设所有分配目标命中，使用简化亮度公式，无真实天气、指向损失或官方故障。
estimated_required_completed 是规划器根据反馈估计的达标数，不是官方计分器输出。

| 起点 | 策略 | 估计完成必观测 | CPU 秒 | 决策数 |
|---|---|---:|---:|---:|
| 正常 | 原策略 | 510 | 21.8 | 177 |
| 正常 | 救援 | 601 | 40.8 | 264 |
| 人为设置每个必观测失败20次，再维修 | 原策略 | 75 | 15.5 | 110 |
| 同上 | 救援 | 601 | 49.5 | 264 |

四次都走完两晚，未耗尽预算。CPU 数字是单次运行测量，部分进程并行，不能当成严谨性能基准。
救援版决策较多，完整卡可能更早触发降档；900秒整场预算尚未验证。不能将两晚结果线性外推到赛季或声称净增10000。

复现：
```
python tools/rescue_probe.py
python tools/rescue_probe.py --rescue
python tools/rescue_probe.py --repair
python tools/rescue_probe.py --repair --rescue
python -m pytest -q
```

上传名称建议 rescue-v1。先与 pro-fast-fault-v4 / duty-log-delivery-fix 对比 B1 的实际总分、漏必观测数、终止原因和CPU，再决定最终版本。勿覆盖旧版本。
